Schema — sem-views / sem-view

Contract per conventions.md v0.5. BDD source of truth for test/e2e/sem-views.cy.js. Changes here precede spec changes precede code. This document renders spec/schema/sem-views.md; the Markdown file remains the editing source.

A named set of alternative presentations of one topic — tabs by another name, kept general on purpose: the active view can be deep-linked, which is why the state lives in the hash and why the name avoids tab.

Authoring form

<sem-views id="delivery">
  <sem-view name="summary" active>
    <p>Short version.</p>
  </sem-view>
  <sem-view name="detail">
    <p>Long version.</p>
  </sem-view>
</sem-views>

Class-form alias (conventions Appendix A): div.sem-views[id] › div.sem-view[data-name], data-active marker.

  • name (required, each view): the view token used in links; document-unique within the container.
  • active: flag — the initial view; the first view is active when absent everywhere.
  • id (container): anchor for deep links — #delivery/detail (bare segment) and the query form #…&sem-views=delivery/detail are the same state.
  • Nested sem-views compose: #outer/inner chains.
Q3 resolved (this branch): the element is sem-views, not sem-perspectives.

Rendered form

  • Fallback: a segmented control (one segment per view name) + view bodies; the active body visible, others hidden; the state marker moves.
  • Deep links: on load and on every hashchange, the state resolver (src/shared/state.ts) scans the hash for a bare container/view segment whose container matches; matches set the active view; the bare segment survives next to other hash params (sem-audience etc.).
  • Upgraded: same DOM contract, animated transitions.
  • JS-off: all views visible in authored order — the state markers are invisible to CSS by design, so a static page reads top to bottom.

Events

  • sem-view-change, cancelable — before the active view switches; canceling blocks the switch (the hash still updates, the DOM follows the resolver, not the reverse).

A11y contract

  • The control is a real tab pattern where tab semantics fit (tablist/tab/tabpanel) or a segmented group of buttons — either way the active segment is aria-selected/aria-pressed.
  • Keyboard: arrows move between segments, Enter/Space activate; focus is not trapped.
  • JS-off, all panels visible: no roles are removed — the panels read as ordinary sections.

Machine contract

  • Each sem-view mints a record; fields.name; prose text = the view body.
  • Extraction reads every view, visible or not — data-active is excluded from records by design (extraction §5c); a consumer that needs "which view did the author feature first" reads a durable qualifier (kind, tags) authored on the view.
  • The invariant holds across switching and across deep links: E(D) is identical in every state.
